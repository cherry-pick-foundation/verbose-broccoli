# gws v0.22.5 runtime security review

- Version: `v0.22.5`
- Commit: `705fb0ecac6f4249679958f6325b809b63fdde17`
- Review date: 2026-09-30
- Runtime-only verdict: **install with limits**
- Findings: **high 0, medium 4, low 3, info 3**

## Scope and method

This was a read-only source review of the login and normal-command paths in `crates/google-workspace-cli/src/{main.rs,auth.rs,auth_commands.rs,credential_store.rs,token_storage.rs,oauth_config.rs,fs_util.rs,logging.rs,client.rs,executor.rs,discovery.rs,services.rs,setup.rs}`, every `crates/google-workspace/src/*.rs` file, the runtime-changing Cargo features, and targeted callers and helpers. Paths below are relative to `.local/gws/src-v0.22.5`. The review did not run or build `gws`, sign in, contact Google APIs, or inspect Workspace data. Release provenance, dependency advisories, and agent skills belong to the separate Reviewer B report.

The source identity was checked with `git -C .local/gws/src-v0.22.5 rev-parse HEAD` and `git -C .local/gws/src-v0.22.5 describe --tags --exact-match HEAD`; the outputs were the commit and tag above. `Cargo.lock:648-649`, `:1368-1369`, `:2143-2144`, and `:3826-3827` pin `dotenvy 0.15.7`, `keyring 3.6.3`, `reqwest 0.12.28`, and `yup-oauth2 12.1.2`. Read-only dependency-source checks used the local Cargo registry and `gh api` against the `yup-oauth2` `v12.1.2` tag. `npm run workflow` and `npm run verify` were not run because both write repository receipts outside this reviewer's assigned report.

## Verdict

The runtime can support the planned narrow use only with the controls below. The prebuilt Linux binary does not persist its encryption key in Secret Service, every invocation searches the working directory and its parents for `.env`, the OAuth loopback flow has neither `state` nor Proof Key for Code Exchange (PKCE), and a writable fresh Discovery cache can redirect authenticated API traffic. These limits require a private config directory, a trusted working directory outside repository trees, controlled login, and restricted commands and egress. This runtime verdict does not approve the release as a whole or override the independent dependency/provenance verdict.

## Findings

### F-01 — Medium — The Linux release uses a file key, not Secret Service

On Linux the CLI declares `keyring` without a persistent backend feature, while the release workflow builds without feature overrides. `keyring 3.6.3` therefore selects its mock backend. The CLI knows this and always synchronizes or creates `.encryption_key`; the default `keyring` label does not mean the installed Secret Service is used. Credentials and token caches use AES-256-GCM with a random 12-byte nonce, but the raw 32-byte key and ciphertext are in the same config directory. This protects against disclosure of one ciphertext file, not a copy or compromise of the whole directory. Evidence: `crates/google-workspace-cli/Cargo.toml:70-77`, `.github/workflows/release.yml:82-88`, `crates/google-workspace-cli/src/credential_store.rs:148-195`, `:258-339`, `:350-417`, and `:425-455`. The exact dependency check `nl -ba ~/.cargo/registry/src/*/keyring-3.6.3/src/lib.rs | sed -n '245,270p'` showed lines 255-269 selecting `mock` when Linux storage features are absent; its `Cargo.toml:56-80` lists the required Secret Service features.

The default directory is `~/.config/gws`, unless the explicit config variable is set or an older platform-specific directory already exists. `.encryption_key`, `credentials.enc`, `client_secret.json`, `token_cache.json`, `sa_token_cache.json`, and login's `credentials.tmp` live there. Atomic secret writes create files as `0600`; credential and token saves set the containing directory to `0700`. The encrypted token maps contain access token, refresh token, expiry, and optional identity token, keyed by a sorted scope set. `credentials.json`, an explicit credentials file, and ADC are plaintext fallbacks whose existing modes `gws` does not repair. Evidence: `crates/google-workspace-cli/src/auth_commands.rs:181-229` and `:311-345`; `crates/google-workspace-cli/src/oauth_config.rs:55-97`; `crates/google-workspace-cli/src/fs_util.rs:20-39` and `:44-106`; `crates/google-workspace-cli/src/token_storage.rs:23-29` and `:39-118`; `crates/google-workspace-cli/src/auth.rs:203-229` and `:335-424`. The cache fields were confirmed by `gh api 'repos/dermesser/yup-oauth2/contents/src/types.rs?ref=v12.1.2' --jq .content | base64 -d | nl -ba | sed -n '54,71p'`.

### F-02 — Medium — Every invocation loads the nearest ancestor `.env`

Before argument parsing or logging setup, `gws` calls `dotenvy::dotenv()`. Version 0.15.7 starts at the current directory, searches parents to the filesystem root, and fills variables that are absent from the existing process environment. Running from a repository worktree therefore lets that worktree's `.env` choose credential files, a config directory, proxies, logs, or Model Armor sanitization. Sanitization sends the full JSON response text to a regional Model Armor endpoint under a cloud-platform token. Evidence: `crates/google-workspace-cli/src/main.rs:48-54`, `:191-201`, and `:477-500`; `crates/google-workspace-cli/src/helpers/modelarmor.rs:246-279`; and the exact local dependency checks `nl -ba ~/.cargo/registry/src/*/dotenvy-0.15.7/src/find.rs | sed -n '24,56p'` and `nl -ba ~/.cargo/registry/src/*/dotenvy-0.15.7/src/iter.rs | sed -n '24,39p'`, which showed current-directory ancestor search and existing-variable preservation.

The variables that affect this path are `GOOGLE_WORKSPACE_CLI_TOKEN`, `GOOGLE_WORKSPACE_CLI_CREDENTIALS_FILE`, `GOOGLE_WORKSPACE_CLI_CLIENT_ID`, `GOOGLE_WORKSPACE_CLI_CLIENT_SECRET`, `GOOGLE_WORKSPACE_CLI_CONFIG_DIR`, `GOOGLE_WORKSPACE_CLI_KEYRING_BACKEND`, `GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_WORKSPACE_PROJECT_ID`, `GOOGLE_WORKSPACE_CLI_LOG`, `GOOGLE_WORKSPACE_CLI_LOG_FILE`, `GOOGLE_WORKSPACE_CLI_SANITIZE_TEMPLATE`, and `GOOGLE_WORKSPACE_CLI_SANITIZE_MODE`. `HTTP_PROXY`, `HTTPS_PROXY`, and `ALL_PROXY`, including lowercase forms, select the proxy OAuth path and are also consumed by `reqwest`; `NO_PROXY` and `no_proxy` affect proxy bypass. `HOME` selects the primary and Application Default Credentials (ADC) locations, while `USER` or `USERNAME` selects the keyring entry name. Evidence: `crates/google-workspace-cli/src/auth.rs:28-35`, `:83-95`, `:203-237`, and `:335-424`; `crates/google-workspace-cli/src/auth_commands.rs:311-345` and `:717-749`; `crates/google-workspace-cli/src/credential_store.rs:148-174` and `:362-369`; `crates/google-workspace-cli/src/logging.rs:21-47`.

### F-03 — Medium — The OAuth loopback flow has no state or PKCE check

The proxy flow binds an ephemeral port on `127.0.0.1`, advertises `http://localhost:<port>`, accepts the first connection, extracts only `code`, and exchanges it without a `code_verifier`. Its authorization URL has no `state` or PKCE challenge. The normal `yup-oauth2` path has the same properties: an ephemeral `127.0.0.1` listener and code-only callback. A malicious local process or browser page can race or inject a code during login. The random port, loopback bind, and single-use authorization code reduce but do not remove this login cross-site request forgery and interception risk. Evidence: `crates/google-workspace-cli/src/auth_commands.rs:37-109`, `:112-162`, and `:181-229`. The exact check `gh api 'repos/dermesser/yup-oauth2/contents/src/installed.rs?ref=v12.1.2' --jq .content | base64 -d | nl -ba | sed -n '45,75p;225,255p;265,300p;345,415p'` showed no `state`, `code_challenge`, or `code_verifier`, the `127.0.0.1:0` bind, and code-only callback parsing.

### F-04 — Medium — A fresh Discovery cache controls authenticated API destinations

Discovery documents are cached for 24 hours at `$GOOGLE_WORKSPACE_CLI_CONFIG_DIR/cache/<service>_<version>.json`. A fresh cached document is parsed without origin, scheme, ownership, or mode checks. Normal and upload requests then use its `baseUrl`, `rootUrl`, and upload paths directly and attach the bearer token, query values, JSON body, or upload bytes. A process that can alter this cache can direct those values to an arbitrary HTTP or HTTPS host. New cache directories and files use the process umask rather than explicit modes. Evidence: `crates/google-workspace-cli/src/discovery.rs:22-32`, `crates/google-workspace/src/discovery.rs:186-217` and `:248-257`, and `crates/google-workspace-cli/src/executor.rs:159-233` and `:540-657`.

### F-05 — Low — `auth status` makes live calls and puts the access token in a URL

`gws auth status` is not a local-only inspection. It reads and decrypts credentials, refreshes the access token, calls userinfo, sends the access token as the `access_token` query value to `/tokeninfo`, and may spawn `gcloud services list`. The command prints paths, project ID, masked client IDs, account email, granted scopes, enabled APIs, and token validity, but not the token itself. Query placement can expose the token to endpoint or trusted-intercepting-proxy logs. Evidence: `crates/google-workspace-cli/src/auth_commands.rs:1202-1344`, `:1346-1447`, especially `:1403-1410`, and `crates/google-workspace-cli/src/setup.rs:820-850`.

### F-06 — Low — Export, logout, and decrypt failure have sharp credential effects

`gws auth export` reads only `credentials.enc`; by default it masks the client secret and refresh token, while `--unmasked` prints them. If decrypted content is not valid JSON, the default path prints it unchanged. `auth logout` deletes `credentials.enc`, the selected plaintext credentials path, both token caches, and the timezone cache, but leaves `.encryption_key`, `client_secret.json`, Discovery cache, and logs. If an encrypted credential cannot be decrypted during a normal command, the loader automatically deletes it and both token caches before trying plaintext or ADC. A poisoned `GOOGLE_WORKSPACE_CLI_CREDENTIALS_FILE` can also make logout delete an unintended user-owned file. Evidence: `crates/google-workspace-cli/src/auth_commands.rs:683-715` and `:1456-1474`; `crates/google-workspace-cli/src/auth.rs:335-424`.

### F-07 — Low — Output, arguments, and opt-in logs remain data-bearing surfaces

Access and refresh tokens remain in memory and HTTPS bodies or headers. They are not passed to subprocess arguments, and the only OAuth temporary file, `credentials.tmp`, is AES-256-GCM encrypted with mode `0600` and removed after the normal login result; a crash can leave it. The CLI's own tracing records method ID, HTTP method, status, latency, content type, upload flag, page number, service/version, paths, and timezone, not bearer tokens, request bodies, or successful document bodies. However, OAuth and API response error bodies can be copied into errors, Calendar timezone failures trace such errors, successful responses are printed to stdout, and JSON request bodies supplied with `--json` are visible in the `gws` process arguments. A server or trusted-intercepting proxy that echoes a submitted secret could therefore place it in error output. `GOOGLE_WORKSPACE_CLI_LOG_FILE` accepts any directory and creates rotating files under the process umask. Evidence: `crates/google-workspace-cli/src/auth.rs:47-80`; `crates/google-workspace-cli/src/auth_commands.rs:37-72` and `:181-229`; `crates/google-workspace-cli/src/logging.rs:15-27` and `:45-74`; `crates/google-workspace-cli/src/executor.rs:241-333`, `:450-487`, and `:753-812`; `crates/google-workspace-cli/src/timezone.rs:77-101` and `:166-171`; `crates/google-workspace-cli/src/error.rs:60-100`; `crates/google-workspace-cli/src/main.rs:62-64` and `:213-224`.

Outside the config directory, normal commands may read `--upload` files and create `-o/--output` or default `download.<ext>` files, all confined after resolution to the current directory. Output creation is not atomic and uses the process umask. Other reads are an explicit plaintext credentials file, explicit ADC file, or well-known `~/.config/gcloud/application_default_credentials.json`; an opt-in log directory is also arbitrary. Discovery and timezone caches stay inside the config directory. Evidence: `crates/google-workspace/src/validate.rs:162-215`; `crates/google-workspace-cli/src/executor.rs:339-376` and `:867-918`; `crates/google-workspace-cli/src/auth.rs:203-229` and `:335-424`; `crates/google-workspace-cli/src/discovery.rs:22-32`; `crates/google-workspace-cli/src/timezone.rs:63-79`.

### F-08 — Info — Network, TLS, proxy, and cache map

The static and document-derived network paths are:

| Host or destination | When | Data sent |
|---|---|---|
| `accounts.google.com` | Browser authorization, and non-proxy authorized-user refresh inside `yup-oauth2` | Browser URL has client ID, redirect URI, scopes, offline access, and account prompt; refresh POST has client ID, client secret, refresh token, and grant type. |
| `oauth2.googleapis.com` | Login token exchange; proxy refresh; `auth status`; `auth setup` brand operations | Authorization code or refresh token with client credentials; status puts the access token in `/tokeninfo` query; setup sends a `gcloud` bearer token plus project, app title, and support email. |
| `www.googleapis.com` | Standard Discovery fetch, login/status userinfo, Calendar timezone, and API calls whose Discovery document selects this host | Discovery service/version without bearer token; other calls carry bearer token, quota project, parameters, JSON or upload data as applicable. |
| `<service>.googleapis.com` and any `baseUrl`/`rootUrl` in the Discovery document | Fallback Discovery fetch and normal API calls | Fallback sends service/version without auth. API requests send bearer token, parameters, bodies, or upload bytes. For the planned services, expected names include `drive`, `docs`, `sheets`, `slides`, `forms`, and `calendar`, but the source does not enforce those hosts. |
| `modelarmor.<location>.rep.googleapis.com` | Only with `--sanitize`, `GOOGLE_WORKSPACE_CLI_SANITIZE_TEMPLATE`, or Model Armor helper commands | Cloud-platform bearer token and the full serialized response or supplied text. |
| Proxy and redirect destinations | When proxy variables are set or a server redirects | The proxy transports the requests above. The client uses reqwest's default redirect policy; the CLI has no destination allowlist. |

Evidence: `crates/google-workspace-cli/src/auth.rs:47-80` and `:243-275`; `crates/google-workspace-cli/src/auth_commands.rs:37-88`, `:662-680`, and `:1363-1410`; `crates/google-workspace/src/discovery.rs:219-246`; `crates/google-workspace-cli/src/executor.rs:159-233` and `:540-657`; `crates/google-workspace-cli/src/helpers/modelarmor.rs:83-87` and `:246-279`; `crates/google-workspace-cli/src/setup.rs:855-896`. The non-proxy refresh endpoint and form were confirmed with `gh api 'repos/dermesser/yup-oauth2/contents/src/authorized_user.rs?ref=v12.1.2' --jq .content | base64 -d | nl -ba | sed -n '41,70p'`.

The HTTP clients use `reqwest` with Rustls and the native operating-system root store; hostname and certificate verification and Server Name Indication are enabled, all Rustls-supported protocol versions are accepted, and there is no certificate pinning or CLI-set minimum version. The loopback OAuth callback is plain HTTP by design. `reqwest` automatically consumes `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, and lowercase forms, including SOCKS in the CLI build, and honors `NO_PROXY`/`no_proxy`; the CLI does not disable this behavior. Evidence: `crates/google-workspace-cli/Cargo.toml:35-48`, `crates/google-workspace/Cargo.toml:28-36`, and `crates/google-workspace/src/client.rs:27-42`. The exact dependency check `nl -ba ~/.cargo/registry/src/*/reqwest-0.12.28/src/async_impl/client.rs | sed -n '292,325p;410,425p;683,745p'` showed verification on, automatic system proxies, native roots, and Rustls version selection.

### F-09 — Info — No telemetry, crash reporting, or binary update mechanism was found

There is no telemetry, analytics, crash-reporting, self-update, version-check, or binary-download path in the reviewed binary source or manifests. `--version` prints the compile-time package version. Local tracing is disabled unless one of the two logging variables is set. The exact command `rg -n -i 'telemetry|analytics|sentry|crashlytics|crash report|self[-_ ]?update|update[-_ ]?check|check for update|latest version' crates/google-workspace-cli/src crates/google-workspace/src crates/google-workspace-cli/Cargo.toml crates/google-workspace/Cargo.toml Cargo.toml Cargo.lock` exited 1 with no output. Evidence: `crates/google-workspace-cli/src/main.rs:102-110` and `crates/google-workspace-cli/src/logging.rs:37-52`. The npm wrapper is outside this review.

The binary does not launch a browser or shell. It prints the OAuth URL for the user. The only operating-system subprocess is `gcloud` in setup/status paths. `auth setup` checks `gcloud version`; may run `gcloud auth login`, inspect or change the active account and project, list or create projects, print an access token, list and enable services, call the OAuth brand REST endpoint, and optionally invoke login. In non-interactive setup it selects every known Workspace API before enabling, so it is especially unsuitable for this plan. Evidence: `crates/google-workspace-cli/src/auth_commands.rs:539-570`; `crates/google-workspace-cli/src/setup.rs:429-472`, `:492-656`, `:743-850`, `:855-896`, `:1204-1214`, `:1338-1386`, and `:1476-1482`; the source-wide `rg -n 'std::process::Command|tokio::process::Command' crates/google-workspace-cli/src` found subprocess construction only in `setup.rs`.

### F-10 — Info — Explicit planned scopes are not silently widened

`--scopes` splits on commas, trims whitespace, and keeps order. The custom list then passes through one special filter that removes `gmail.metadata` only when a broader Gmail scope is already present, after which `openid`, `userinfo.email`, and `userinfo.profile` are appended if missing. Therefore the planned `drive.file` and `calendar.app.created` values pass unchanged and receive only those three identity scopes. Refresh-token requests contain no scope field and cannot widen the grant. Later commands choose a Discovery-advertised method scope for token lookup, but that does not trigger new consent; an operation outside the existing grant fails. Model Armor helpers request `cloud-platform`, but likewise cannot add it silently to the existing authorization. Evidence: `crates/google-workspace-cli/src/auth_commands.rs:485-511`, `:595-614`, `:752-768`, and `:848-879`; `crates/google-workspace-cli/src/auth.rs:47-80` and `:243-275`; `crates/google-workspace-cli/src/main.rs:259-265`; `crates/google-workspace-cli/src/helpers/modelarmor.rs:246-255`. The non-proxy refresh body was confirmed in `yup-oauth2 v12.1.2` by the exact `gh api` command in F-08; its `authorized_user.rs:41-70` ignores the passed scopes and sends only client ID, client secret, refresh token, and grant type.

## Required controls

1. Do not install or use this release if persistent Secret Service storage is a requirement. The supplied Linux binary cannot meet it. If accepting file-key storage, set `GOOGLE_WORKSPACE_CLI_KEYRING_BACKEND=file` so status is honest, and treat the entire config directory as a credential secret.
2. Set `GOOGLE_WORKSPACE_CLI_CONFIG_DIR=/home/choi-eunchang/.config/gws-cherry-pick` before every invocation. Pre-create it as the user with mode `0700`. Keep `client_secret.json`, `.encryption_key`, `credentials.enc`, `token_cache.json`, `sa_token_cache.json`, and any remaining `credentials.tmp` at `0600`. Keep the directory outside repositories, sync folders, shared backups, and agent-editable trees.
3. Never run `gws` from a repository worktree or any directory with a `.env` in it or an ancestor. Use a dedicated private staging directory outside repository trees, with mode `0700` and `umask 077`; copy only approved upload inputs into it and move reviewed outputs out afterward. This changes the planned worktree execution model.
4. Before login and agent commands, unset `GOOGLE_WORKSPACE_CLI_TOKEN`, `GOOGLE_WORKSPACE_CLI_CREDENTIALS_FILE`, `GOOGLE_WORKSPACE_CLI_CLIENT_ID`, `GOOGLE_WORKSPACE_CLI_CLIENT_SECRET`, `GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_WORKSPACE_PROJECT_ID`, `GOOGLE_WORKSPACE_CLI_LOG`, `GOOGLE_WORKSPACE_CLI_LOG_FILE`, `GOOGLE_WORKSPACE_CLI_SANITIZE_TEMPLATE`, and `GOOGLE_WORKSPACE_CLI_SANITIZE_MODE`, except for a value deliberately required and reviewed for that invocation. Keep all proxy variables, including lowercase forms and `NO_PROXY`/`no_proxy`, unset for login and normal use.
5. Create the Internal consent screen and Desktop client manually. Never run `gws auth setup`. Log in interactively on the trusted machine with exactly `gws auth login --scopes https://www.googleapis.com/auth/drive.file,https://www.googleapis.com/auth/calendar.app.created`; do not use `--services`, `--readonly`, `--full`, or default interactive scope selection. Verify the printed account is in `cherry-pick.org` and that the printed scope list contains only the two requested scopes plus the three identity scopes.
6. Treat login as a sensitive ceremony: use a trusted browser session, close unrelated untrusted pages, complete the flow once, and verify the resulting account. Do not expose the printed authorization URL. A strict requirement for OAuth `state` and PKCE means this release must not be used.
7. Agents must not run `auth status`, `auth export`, `auth logout`, `--sanitize`, Model Armor helpers, or `auth setup`. A user may run status/export/logout only from the trusted staging directory after checking the environment; never capture `auth export --unmasked` output in logs or repository files.
8. Restrict egress to `accounts.google.com`, `oauth2.googleapis.com`, `www.googleapis.com`, and the exact `*.googleapis.com` service hosts needed after trusted Discovery inspection. Block Model Armor hosts. Protect `$GOOGLE_WORKSPACE_CLI_CONFIG_DIR/cache` from modification by other users and untrusted tools; investigate and remove the cache if tampering is suspected.
9. Keep CLI logging disabled. Treat stdout, stderr, shell/process argument capture, and downloaded files as potentially containing Workspace data. Do not put sensitive document content directly in `--json` arguments when other same-user processes or durable shell history are outside the trust boundary.
10. These controls are prerequisites, not final approval. The coordinator must combine this runtime report with the independent release/dependency and agent-skill report before installation.
